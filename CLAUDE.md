# Game Feed: instructions for Claude

Nabeel is building a TikTok-style feed of mini-games: swipe up and a random game starts instantly. Games are built one at a time; he play-tests each as a hosted page, gives feedback, and approves it. Goal: 1,000 games. He is not technical; talk in plain words.

## At the start of every session
1. Read `games.json` (the official registry) and `LEDGER.md`. If he asks "where are we?", answer from these: number of games, each game with its status and play link, the feed app (`feed_app` in games.json: its page and its Android download), and what's next.
2. Check `planned` in `games.json`: the next game may already be designed, with its full spec in `specs/`. If he says "build the next game", build that one.
3. Read `LESSONS.md` and follow it: his taste, the rules every game must pass, how to test, and build notes for each existing game. Reuse code from the most similar existing game in `games/<id>/index.html`.
4. **Engagement factors are mandatory in every game, without being asked.** "Engagement factors" is Nabeel's name for the research in `PLAYBOOK.md`. Read it before designing or changing a game: the design principles (P1–P30), the **Satisfying Sounds** rules and sound kit (S1–S11), the checklist and the AVOID list. Pick 3–5 principles that suit the game (never all of them) and record them in the spec and in the game's `principles` field in `games.json`. The sound rules apply to every game.

## Adding or changing a game
1. Put the engagement factors in from the first build (the chosen principles, the sound rules, juice, haptics, honest feedback, personal best, help after losses where it fits). Never ship a game without them.
2. Build the game as one self-contained `games/<id>/index.html` (canvas, inline JS/CSS, Google Fonts with fallbacks, synthesized sounds built from the PLAYBOOK sound kit). Give it its own `storage_prefix` for saves. Give it an **instant start** for the feed from the first build: `window.gameFeedStart('mini')` must have him playing within a second of tapping its card, with no menu, countdown or intro, at his own level, without changing who wins (LESSONS rule 7). Give it the **basic controls** from the first build too (LESSONS rules 4 and 11): it remembers the level he is on (a win moves it on at once; lower levels open, higher ones locked), and its pause menu is always Resume, Restart, Levels (`#pResume`, `#pRestart`, `#pLevels`, plus `window.gameFeedLevels()` for the feed).
3. Test it (see LESSONS.md, including fast-forward cheat tests; add it to `tools/test_controls.py` and run that), then publish it as an artifact so he can play it; republish the same artifact for each revision.
4. When he approves it: add or update its entry in `games.json` (next number; never renumber; bump `version` on changes), run `python3 tools/ledger.py`, add its build notes and any new lessons to `LESSONS.md`, then commit and push. GitHub runs `tools/check.py`, which loads every game and fails on errors or registry mistakes.
5. Statuses: `in-progress` (being built), `testing` (he's play-testing), `approved` (done), `retired` (removed from the feed, number kept).
6. **Every `testing` or `approved` game is in the feed app automatically.** When a game reaches `testing` (or its look changes): fill in its `feed` fields in `games.json` (`hook`: one short line for its card; `genre`; `intensity` 1-5; `thumbs` 1 or 2; `start`: the button(s) that begin play, default `["#playBtn"]`; `font`: its title font; `mini`: true once it has its instant start; `live`: a JavaScript expression that is true once he is in live play), run `python3 tools/previews.py <id>` to make its card picture and clip (the clip must be the game's most exciting moment and keep the clip rules in LESSONS, "Every clip is the most exciting moment": write `games/<id>/preview.json` for it and look at the sheet in `out/previews/`), `python3 tools/fonts.py` if it uses a font not yet in `feed/fonts/`, then `python3 tools/test_feed.py`, and republish the **Game Feed** page (see below). Pushing to `main` then puts the game into his installed phone app by itself: tell him it will be there the next time he opens the app, a few minutes after the push.

## The feed app (built Nov 2026; read "The feed app" in LESSONS.md before changing it)
- **What it is:** `feed/index.html` is the app. One game card at a time, shuffled; swipe up for the next, down for the last; each card plays a short silent clip of the game and a tap starts it; the bar under the card has **Games** (the list, with search), **Sound** (one switch that silences or restores every game), the swipe handle, **Pause** (while a game is running) and **Pin**. A paused game shows the same three controls every game has in its own pause menu: **Resume, Restart, Levels**. After about ten games a soft "That's a set" card (PLAYBOOK P27).
- **Where the games come from:** `python3 tools/build_feed.py` builds the whole app into `out/app/` from `games.json`: the feed page, `games.js` (the list), every `testing`/`approved` game with the plug (`feed/plug.js`) put at the top of its page, the card pictures and clips, and the fonts. Nothing inside a game has to change for the feed. The same folder is the hosted page and the inside of the Android app.
- **The plug** lets the feed start any game (it presses the game's own Play button, `feed.start`), freeze it completely when he swipes away or the app is hidden (frames, timers, clock and sound all stop) and carry on from the same instant. **A tap on a card drops him straight into the action:** the plug calls the game's `window.gameFeedStart('mini')` (every game has one, or needs none; see LESSONS rule 7), so there is no menu, countdown or intro between the tap and play. The feed's Levels button calls the game's `window.gameFeedLevels()`. A game can do more if it wants: `gameFeedPause()`, `gameFeedResume()`, `gameFeedSound(on)`, and `GameFeed.finish({win, level, score})` to report a finished level.
- **Its page:** `feed_app.artifact` in `games.json`. Republish that same artifact (all files in `out/app/`, mode replace) after any change to the feed or to a game in it.
- **Android app:** `android/` is a small wrapper around `out/app/`. On every push to `main`, after the checks pass, GitHub builds `GameFeed.apk` and attaches it to a new Release; the newest is always at `feed_app.apk`. It is signed with `android/signing/release.p12`, whose password is the `KEYSTORE_PASSWORD` Actions secret (only Nabeel can add it; without it GitHub still proves the app builds, but makes no `GameFeed.apk`).
- **New games reach his phone by themselves; anything app-wide comes as a new download.** Both halves are his rules (LESSONS, "New games arrive by themselves"). He will never stop adding games and must not have to update anything to get them: after the checks pass, the `publish` job puts the built app on the **`app-v2`** branch (`feed_app.published`); every time the phone app opens (and at most every 10 minutes while it stays open) it reads `manifest.txt` from there and fetches whatever is new or changed into a folder on the phone (`android/.../Sync.java`); the feed adds new games to what it is showing, as the next cards, marked New, without reloading anything. This covers games, card pictures, clips, fonts and the list. **The feed page (`feed/index.html`) and the Java in `android/` only reach him inside a new APK**: when either changes, check the new `GameFeed.apk` and tell him plainly that this one needs installing, with the link (`feed_app.apk`). The plug (`feed/plug.js`) travels with the games, so it must always work with an older feed page: only add to what the two say to each other. Never push to or delete the old **`app`** branch: it is frozen at build 18 for the first installed apps, which restart the feed whenever it changes. Read "New games arrive by themselves" and "What went wrong in builds 15 to 18" in LESSONS.md before touching `Sync.java`, `MainActivity.java`, `manifest.txt`, `GameNative` or the publish job.
- **Tests:** `python3 tools/test_feed.py` plays the feed in a phone-sized browser (every game starts from one tap, freezes solid, Pause on the bar, Resume, Restart and Levels on the Paused card, swiping, order, pin, search, break card, back button, phone-app loading). `python3 tools/test_controls.py` plays every game's own basic controls (the level he was on comes back, pause, resume, restart, levels, a win moves the saved level on). `python3 tools/test_sync.py` runs the phone app's real updater against a stand-in for GitHub (first copy, new game, dropped connection, bad files) and then opens the fetched feed. `python3 tools/check_android_java.py` compile-checks the wrapper's Java. GitHub runs the first three after `tools/check.py`, and nothing is published or built unless they pass.
- **What comes next is for later, when he asks:** the "what comes next" brain (now a shuffled deck in `nextGame()`; play history is already kept in `gf.stats` and `gf.log`), taking over a clip at the exact moment he taps it (offered, he chose the instant start instead), and, when there are too many games to keep them all on every phone, fetching a game only when its card comes up.
